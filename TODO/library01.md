# 媒体库禁用、扫描与缺失文件处理方案

## 目标与安全原则

外部媒体库由其他应用或外置/网络存储管理。Tracks 对它们只维护索引，不应因为临时卸载、权限问题或一次不完整扫描而丢失播放列表、播放次数、星标等数据。

核心原则：

1. **禁用不等于删除**：禁用保留该媒体库及其歌曲/播放列表数据，可重新启用；按产品要求，禁用时会另外停止播放并清空全局队列和播放历史。
2. **扫描不自动清理缺失数据**：缺失记录先报告，用户确认后才从 Tracks 索引中删除。
3. **外部文件永不由删除索引操作删除**：删除媒体库只影响 Tracks SQLite 内的索引和关联数据。
4. **删除前先备份主库**：备份失败则取消删除。
5. **临时文件缺失不写入数据库**：扫描/播放时的暂时不可用状态只保存在内存中。

## 当前实现审查

### 数据模型

- `libraries` 表现在只有 `id/path/kind/name/date_added`，没有启用状态。
- `songs` 表没有 `library_id`。歌曲归属目前靠 `songs.path` 是否处于某个扫描根目录下推断。
- 一份 Tracks `library.sqlite` 存放内部库和全部外部库的索引；播放列表、歌曲播放次数、星标等也在该库中。
- `playlist_items` 指向歌曲。删除歌曲会删除其播放列表条目，并清理无引用的专辑/艺人；播放列表本身不会因此自动删除。

### 当前扫描语义

- `Library.init()` 先加载数据库，再调用 `rescanAll()`；所以启动时先显示已有数据库内容，随后后台扫描。
- `LibraryScanner.pendingFiles` 会遍历支持的文件，按已知 path、mtime 和 file size 跳过未变化文件。当前所谓普通扫描属于“新增 + 变化文件增量解析”，不是纯新增扫描，也不是全量重新解析。
- `rescanAll(force: true)` 不提供 known-file 快速跳过，会重新解析所有发现的文件；封面缓存重建使用此路径。
- 全库扫描完成后调用 `prune(roots:)`；单库 Rescan 完成后调用 `pruneSongs(under:)`。如果根目录存在，这两个路径会直接删除数据库中找不到的歌曲，无缺失清单，也无逐项确认。
- 全库 prune 对不存在的扫描根目录会保留其歌曲，这是对不可访问存储的保护；但它只检查根路径存在性。遍历失败和权限不足没有可靠地区分。
- `pendingFiles` 对 `FileManager.enumerator` 创建失败时直接跳过目录，没有将“扫描不完整”传回调用方。若目录路径仍然存在，后续 prune 可能把遍历不到的歌曲当作缺失。
- `openInternalLibrary` 对缺失的内部歌曲会显示警告并跳过自动扫描，避免立刻 prune；外部根目录不可用时会显示警告，但普通扫描本身仍没有明确的扫描完整性结果。
- 内部库虽然设计上以导入为主，但用户可打开 `Music` 文件夹，因此不能假定用户不会在 Tracks 外添加、修改或删除文件。
- 内部库已有 `rebaseSongs(from:to:)`：打开一个搬到新位置的 Tracks 内部库时，按旧根目录下的相对路径改写歌曲绝对路径，并保留歌曲 ID。外部库没有对应的迁移入口；换卷标或从本地卷移动到外置卷后，添加新路径会被视作另一个库，旧路径及其歌曲记录仍留在数据库。

### 当前移除外部库

- Settings 当前已有一次“Remove External Library?” 确认，但确认后直接移除 `libraries` 记录，再用剩余根目录执行 prune；没有“先禁用、后删除”的阶段，也没有删除前备份。
- 若仍有其他配置根目录，原外部库中不再归属任何 root 的歌曲会被删除，相关 playlist item、播放次数、星标等歌曲数据随歌曲记录消失。
- 若移除后没有任何扫描根目录，当前代码会跳过 prune，数据库行暂时保留；这与“显式删除”语义不一致。
- `removeExternalLibrary` 通过 `applyUpdatedSongs` 更新队列；队列中已不在数据库的歌曲会保留旧对象。移除流程需要显式处理播放中和排队中的歌曲。

### 当前播放失败处理

- `beginCurrentTrack` 直接为路径创建 `AVPlayerItem`，并在确认播放成功之前增加播放次数/历史。
- 如果 `AVPlayerItem` 失败，`tick()` 会释放 AVPlayer 后按歌曲时长模拟播放；不会将其加入缺失状态，也不会立即跳过。
- `Song` 没有运行时缺失字段；专辑轨道行目前在轨道号位置显示当前播放图标，歌曲表在状态列显示播放/暂停图标，没有缺失提示图标。

## 建议的扫描定义

“启动时刷新”和“Quick Scan”不应成为两套功能。**启动时自动运行 Quick Scan** 即可；数据库加载是单独的初始呈现步骤。

### Quick Scan

- 只发现并导入尚未入库的新文件。
- 不重新解析已有记录，不检查缺失，不删除任何数据库记录。
- 启动时可以后台自动执行同一 Quick Scan；用户从 Library Manager 手动触发时也走相同策略。

### Full Scan

- 先验证媒体根目录存在、可读，并且目录遍历完整成功。**不检查或记录卷标、卷 UUID、文件系统身份等信息。**
- 导入新增文件。
- 检查已有文件变化；只比较 mtime 和 file size，有变化时重新读取 metadata 并更新数据库。禁止计算或保存文件内容哈希。
- 收集数据库中属于该库、但本次完整遍历没有发现的歌曲，形成待确认的缺失清单。
- **不自动删除缺失记录**。用户确认后，只删除用户选中的歌曲索引及其关联数据。
- 缺失候选逐首列成表格，并提供搜索框；用户可按歌曲信息或路径搜索、逐项选择是否从 Tracks 索引移除。Full Scan 的缺失项与 Relocate 的未匹配项使用同一个审核窗口，不为两种来源实现两套 UI。
- Full Scan 如果没有文件丢失差异，不显示缺失审核窗口。Relocate 如果没有未匹配项，直接完成迁移，也不显示 Keep/Delete 审核窗口。

文件变化检测只使用 mtime + file size；不计算、不保存文件内容哈希，也不提供哈希扫描模式。

### 扫描完整性与目录可读性检查

扫描结果不能只返回 `[ScannedTrack]`；至少需要包含：扫描根、完成/取消/失败状态、目录遍历是否完整、发现的路径集合、新增/修改歌曲、缺失候选及错误信息。

- 根目录不存在、不可读、enumerator 创建失败、任务取消或目录遍历未完整结束，都必须使本次扫描不能执行缺失删除。
- **不检查或记录卷身份**。只要记录的媒体目录存在、可读且完整遍历成功，就将本次结果视为有效；即使没有发现任何旧文件，也照常列出缺失清单并询问用户是否删除。
- 对权限错误、网络目录读取错误或扫描不完整，应显示错误且不生成可执行删除的缺失清单。
- 缺失报告应可复制，至少包含文件路径、歌曲/专辑信息和缺失数量；最好可按歌曲/专辑选择删除。

## 媒体库根路径变化和迁移

完整路径变化不一定代表换了一套媒体。卷标变化、存储从本机盘移动到外接盘、挂载目录改变，都可能只是根目录变化，库内文件相对位置保持不变。此时应允许用户把现有媒体库迁移到新位置，而不是“添加一个新库 + 留下旧库”。

### 建议的操作

- 在媒体库管理中提供针对现有库的 **Change Location… / Relocate…** 操作。
- 用户选择新根目录后，Tracks 按旧媒体库根目录下的相对路径匹配：`newRoot + relativePath(oldRoot, storedPath)`。例如 `albumA/1-helloworld.mp3` 和 `albumB/1-helloworld.mp3` 是不同的匹配键。先生成迁移预览，不立即改数据库。
- 预览应包含：旧库歌曲数、按相对路径匹配到的数量、未匹配数量、新位置的额外文件数量、路径规范化冲突，以及无法访问或遍历不完整的错误。
- 用户确认后更新该库根路径，并将所有未勾选删除的歌曲路径按旧根目录相对路径改写到新根目录；不论目标文件是否存在，都更新到新根。保留 Song ID、playlist item、播放次数、stars、history、queue、`date_added` 等关联数据。
- 未匹配的旧歌曲继续保留为缺失候选；额外文件可作为新歌导入。路径迁移本身不能把未匹配项目当作用户确认删除。
- Relocate 产生的未匹配歌曲进入与 Full Scan 完全相同的缺失项审核窗口。用户可搜索并逐首勾选删除；未勾选项保留在数据库、路径仍迁到新根并继续标记/呈现为缺失。未勾选删除的 item 不会阻止根路径迁移。
- 审核窗提供 **Select All** 和 **Deselect All**。Full Scan 左侧按钮为 **Keep**；Relocate 左侧按钮为 **Cancel**，取消 Relocate 不更改库根或歌曲路径。
- 更新 library root、歌曲路径和文件统计信息应放在 SQLite transaction 内；提交前建议也生成一次 SQLite Online Backup 快照。

### 匹配与安全要求

- 匹配依据是相对于媒体库根目录的完整路径，不是 basename。`albumA/1-helloworld.mp3` 与 `albumB/1-helloworld.mp3` 不会相互匹配；目录结构改变的歌曲列为未匹配，不自动猜测。
- 候选新路径必须位于新根目录之下且是受支持的媒体文件。相对路径决定是否匹配；mtime 和 file size 只用于判断文件是否变化及是否需要重新读取 metadata，不计算内容哈希。
- 路径迁移前只需确认新根目录存在、可读且遍历完整；不核对卷/文件系统身份。旧根目录不可访问时，用户仍可选择新根目录并预览相对路径匹配结果。
- 要处理迁移期间文件被移动、重复路径、部分文件匹配、目标路径冲突、符号链接和大小写差异；任一数据库更新失败时整体 rollback。
- 迁移成功后更新现有 `libraries` 记录的 path/name，并刷新内存中的 albums、playlists、queue/history。新旧路径都不应残留为两份同源库。
- 库的 `kind`（Internal/External）表达 Tracks 是否拥有写入管理权，不应仅因存储从内置盘换到外置盘就自动改变。外置位置不等于只读来源；由其他应用管理才是 External 的主要语义。

### 产品语义建议

- 若旧根仍可访问但用户确实想改位置，Relocate 仍应走预览和确认，不直接覆盖 path。
- 若旧根不可访问，允许用户选新位置并基于旧数据库路径相对于已记录旧根的相对路径匹配，但明确标示“原位置当前不可访问”；匹配不足时只提供报告，不允许一键完成或删旧记录。
- 新路径若对应已登记的其他媒体库，应拒绝迁移或提供显式合并流程，不能悄悄合并同路径歌曲、playlist 和计数。
- 对“移动了一部分文件”的情形，迁移只重定位相对路径匹配并确认的旧记录；剩余缺失项进入 Full Scan 缺失清单，额外文件列为新增，不自动清理。

## 外部媒体库：禁用与删除

### 禁用/启用

- `libraries` 增加持久化的 `enabled` 标志，默认 `true`。
- 建议为 `songs` 增加 `library_id`，通过迁移按现有路径/root 归属回填。当前没有歌曲归属字段；继续靠字符串前缀判断会让后续筛选、禁用和删除更脆弱。
- 禁用/启用只更新媒体库级别的 enabled 状态，不批量改写 songs、playlist_items、play counts、stars 或 playlist rows。
- 禁用操作必须先确认并警告：禁用会停止当前播放、清空整个播放队列和播放历史（History）；媒体库歌曲不会再显示在 Albums、Recently Added、Artists、Genres、Songs、搜索结果、播放列表等内容位置。
- 确认后停止播放，清空 queue/base queue，并清空播放历史（History）；按用户要求，这些动作作用于整个播放器状态，不只影响被禁用媒体库中的歌曲。队列持久化记录也要清除。
- 禁用后，歌曲和 playlist item 仍留在数据库，但所有内容查询都隐藏该来源的歌曲；播放列表本身保留，启用来源后其歌曲条目恢复显示。Settings 中的媒体库管理行必须继续可见，以便重新启用或删除。
- 启用只将来源重新纳入浏览、播放和扫描，不恢复禁用时已清空的队列或播放历史（History）。
- 当前播放器的播放历史实际保存在 `UserDefaults` 的 `player.historyIDs`，不是 SQLite 表；当前实现最多保留 50 项（`PlayerState.historyLimit`）。禁用操作需要增加明确的清空历史 API；确认文案使用“播放历史”，不在产品文案中写数量。

### 两阶段删除

1. **启用状态**：提供 Disable 操作；禁用确认后将 `libraries.enabled` 设为 false。
2. **禁用状态**：才显示可用的红色 Delete 操作。
3. 点击红色 Delete 后展示第二次破坏性确认。文案需明确：删除该来源在 Tracks 中的歌曲索引、播放列表关联、播放次数/星标等歌曲数据；**不删除音频文件**。删除后即使用户创建的 playlist 变为空，也保留该 playlist，不删除其本身。
4. 用户确认后先备份，再在一个 SQLite 事务内按 `library_id` 删除该库歌曲及 `playlist_items` 关联，并清理无引用的专辑/艺人、更新 queue/history。
5. 备份或事务失败时保留来源记录和原始数据，展示可复制错误信息。

### 备份要求

- 备份对象是 Tracks 当前主库 `library.sqlite`，不是外部媒体文件夹里的文件。
- SQLite 正常运行时使用 WAL。不能只用 `FileManager.copyItem` 复制主库文件，否则最新已提交数据可能仍在 `-wal` 中。
- 通过 SQLite Online Backup API 从当前连接生成一致快照；备份失败必须中止删除。
- 文件可命名为 `library.sqlite.backup-20261027T143012.123Z`（UTC 时间，毫秒精度）；若发生同名冲突需增加唯一后缀。
- 执行删除前确认备份完整可打开；删除事务提交后可记录备份路径供用户恢复。

## 媒体临时缺失与播放

- 缺失状态只保存在运行时 `Set<Song.ID>`，不写数据库。它表示“本次运行中观察到不可用”，不等于用户确认删除，也不等于来源已禁用。
- 播放开始前检查文件；播放过程中收到可确认的文件不存在错误时，将歌曲加入集合并跳过。成功打开/扫描到该文件后清除此状态。
- 区分“文件不存在”与解码失败、无权限、网络 I/O 错误；后几类不能直接标记为路径缺失。
- 歌曲表的播放状态列、专辑详情轨道号位置、Artists/Genres 中的专辑轨道列表统一显示圆圈叹号。播放列表中同样在播放状态列标记；缺失项禁用播放操作，但保留显示。
- 不要在 SwiftUI 每行 render 时同步查询文件系统；通过播放事件和扫描结果维护内存状态，再将状态传给行组件。
- 连续 100 首确认不存在时暂停队列并提示“可能外置存储已断开”。计数只针对连续的文件不存在错误；成功启动播放时清零。若根卷已不可用，应直接提示/暂停，不必等 100 首。
- 只在 AVPlayer 确认进入可播放状态后记播放次数和历史，避免缺失歌曲被算作播放。

## 实施顺序

1. **先防止自动数据丢失**：Quick/启动扫描和普通 Rescan 不再自动 prune；扫描器必须报告完整性。
2. **增加来源归属与 enabled 状态**：迁移 `libraries.enabled` 和 `songs.library_id`，定义普通浏览、播放列表、队列对 disabled source 的显示/播放策略。
3. **实现 Full Scan 与 Relocate 预览**：扫描缺失清单、路径匹配结果都可复制；Cancel 不改变数据；缺失项和未匹配项只在用户确认后处理。
4. **实现运行时缺失提示和安全跳过**：不持久化缺失位，验证列表图标和 100 连续缺失保护。
5. **实现禁用 → 二次确认删除 → SQLite 在线备份 → 事务删除**。

## 验收清单

- [ ] 启动自动 Quick Scan 与用户 Quick Scan 行为一致：只新增，不改已有 metadata，不清理缺失。
- [ ] Full Scan 能发现新增/修改/缺失；有缺失时显示统一审核窗口，可搜索、Select All/Deselect All 和逐首勾选删除；没有缺失时不弹审核窗。
- [ ] 根目录不存在/不可读、权限拒绝、遍历失败、扫描取消时不出现可执行的删除结果；根路径可读且扫描完整时，即便所有旧文件都缺失，也列清单询问用户。
- [ ] 外部库卷标/挂载路径变化后可 Relocate；按相对路径匹配。无未匹配项时直接迁移且不弹审核窗；有未匹配项时共用 Full Scan 审核窗。
- [ ] Relocate 时所有未勾选删除的歌曲都改写到新根下的相对路径，即使目标文件当前缺失；勾选删除的歌曲及其 playlist 关联删除。Cancel 不改库根或歌曲路径。
- [ ] 部分文件移动时，未匹配项保留并进入审核清单，额外文件标为新增；迁移后 Song ID 和 playlist/play-count/star/history/queue 关联保持不变。
- [ ] 本地卷迁到外接卷只改变存储路径，不会仅因卷类型自动将 Internal/External 类型互换。
- [ ] 禁用前明确警告会停止播放并清空整个队列和播放历史；确认后执行，取消则状态不变。
- [ ] 禁用后该来源歌曲在所有内容位置（包括播放列表条目）隐藏，数据库中的 playlist item 保留；重新启用后歌曲条目恢复。Settings 中仍可看到该禁用库。
- [ ] 禁用确认、红色 Delete、删除确认的顺序正确；外部音频文件从未被移动/删除。
- [ ] 删除前生成毫秒级时间戳备份；WAL 场景下备份可独立打开；备份失败时不删除。
- [ ] 删除后只清理被选来源歌曲及其关联，不误删其他库歌曲；空 playlist 保留；queue/history 无悬挂歌曲。
- [ ] 播放遇到单个缺失文件时显示叹号并跳过，不写缺失状态到数据库；文件恢复后提示消失。
- [ ] 连续 100 个缺失文件会暂停并提示；正常播放成功后计数归零。

## 已确定的产品细节

- 删除来源后，用户创建的 playlist 即使为空也保留。
- Full Scan 缺失项和 Relocate 未匹配项共用同一个表格审核窗口，支持搜索、Select All/Deselect All 和逐首选择是否删除；无差异时不弹窗。
- Full Scan 左侧操作为 Keep；Relocate 左侧操作为 Cancel。Relocate 的未勾选项目仍更新到新根目录下的相对路径。
- Relocate 按根目录下的完整相对路径匹配；相同 basename 位于不同子目录时视为不同歌曲。目录结构改变时列为未匹配项，不自动猜测。
